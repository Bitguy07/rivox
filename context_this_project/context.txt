Concrete plan to convert LingBot-Map outputs into a campus navigation app
1) Capture & reconstruct (build the 3D map)
- Capture: walk the campus corridors and rooms with a phone camera, record continuous video at a steady frame rate, include loop closures and coverage of key corridors/doors.
- Reconstruct: run demo.py (streaming or windowed) on your recorded video / frames to produce:
  - per-frame extrinsics (traj.txt)
  - per-frame world points / per-frame point clouds (points/ or HxWx3 EXR)
  - a global points.ply (points.ply)
- Export: use lingbot_map.vis.glb_export or convert points.ply → mesh/GLB for the mobile viewer (the repo contains glb_export.py and point_cloud_viewer.py).

2) Create a localization index (so you can localize a phone frame in that map)
- Options for initial alignment:
  - Visual localization (recommended for indoors): build an image database of keyframes with known camera poses from the reconstruction and run image retrieval + 2D–3D matching (descriptors → PnP) to get metric camera pose in the map.
    - Tools: COLMAP (descriptor matching + PnP), SuperPoint + SuperGlue, NetVLAD for retrieval; the repo references dataset adapters and a BSS layout with traj/intrinsics you can reuse.
  - AR-based alignment (fast): use ARKit / ARCore on-device for continuous pose (VIO). At app start perform one-shot visual localization (image matching) to compute the transform between the AR coordinate system and LingBot’s map coordinates, then apply that transform continually to align the AR-tracked pose to the map.
  - Hybrid: server-side matching (send compressed frame descriptors to server) if on-device compute is too heavy.
- Implementation notes:
  - The repo outputs metric poses (traj.txt) and point clouds (points.ply); those are the targets to align to.
  - You can precompute descriptors for keyframes (and index them with Faiss) for fast nearest-neighbor retrieval on-device or on a server.

3) Build a navigation graph and pathfinding
- From the dense point cloud / mesh:
  - Manually or semi-automatically extract a walkable graph (nodes at doorways, corridor intersections, classroom entrances). For prototyping: downsample the point cloud, run a voxel grid and cluster, then compute a skeleton / connectivity graph.
  - Alternatively overlay an axis-aligned 2D floorplan from the point cloud (project to floor plane) and discretize it into a navigation grid/graph.
- Pathfinding:
  - Use Dijkstra (or A* with heuristics) on the graph to compute shortest paths. Prototype in Python with networkx, then translate to your mobile environment (Unity C# / Kotlin / Swift).
  - Store the graph on the mobile device or host it on a server and return waypoints.

4) Mobile app + avatar display / continuous tracking
- Preferred approach for indoor accuracy:
  - Native or Unity app that uses ARKit (iOS) or ARCore (Android) for high-frequency VIO and sensor fusion.
  - At session start: run visual localization to get the user’s transform into the map; align AR tracking to the map coordinate system.
  - Continuously update avatar transform from AR pose; show computed route as a 3D overlay (floating arrows, colored path, step-by-step).
- If you must use a hybrid or web approach:
  - Browser-based location is less reliable indoors; use a native app to access raw sensors, higher-rate IMU, local camera frames, and AR libraries.

Practical tradeoffs & suggestions
- On-device localization is the best UX but requires either:
  - Efficient descriptor extraction and a compact index (e.g., MobileNet-based descriptors + Faiss) or
  - Using ARKit/ARCore VIO + a single-shot visual alignment to map coordinates.
- Server-side localization offloads compute but increases latency and requires a reliable network; you can do coarse retrieval on-device and refine server-side.
- For path planning you’ll want a semantic or simplified topological map (doors, floor transitions, stairs) rather than raw dense point clouds; compute and store that separately.

Short answer: Yes — LingBot‑Map does not provide a one‑click “merge multiple recordings into one map” GUI, but the repo already includes the exact building blocks you need (Umeyama + ICP registration, per-frame poses, exported point clouds / traj files, and a GLB exporter). The practical approach is to (A) run the model on each video to produce per‑recording point clouds + trajs, then (B) register those reconstructions into a common frame (Umeyama or geometric registration + ICP), (C) apply the transforms to poses and clouds, and (D) fuse / downsample into a single merged PLY/GLB. Below I explain the options, pitfalls, and give two concrete merging workflows (pose-based and geometry-based) with example code you can run.

How LingBot‑Map helps (what’s already in the repo)
- demo.py / demo_render produce per‑recording outputs (predicted depths, world points, a global points.ply and traj.txt in the repo’s BSS layout). Use those as inputs to merging.
- The repo’s benchmark code includes umeyama_registration and icp_registration (benchmark/benchmark/geometry/registration.py) — Umeyama computes a Sim(3) transform from corresponding points; ICP refines alignment without correspondences.
- The viewer/export code (lingbot_map/vis/glb_export.py, point_cloud_viewer.py) can export and inspect point clouds / GLB after merging.

Two reliable ways to merge recordings
1) Pose-based (preferred when you have overlapping camera poses / matching keyframes)
- When recordings share overlapping views or you can identify corresponding frames (same door / same scene), extract corresponding 3D points (or corresponding camera centers) and use Umeyama (Sim(3)) to compute a similarity transform from recording B → recording A.
- Refinement: apply Umeyama result then run ICP (icp_registration) to refine.
- Advantages: robust when you can match frames; keeps scale issues handled (Umeyama estimates scale).
- Used by the repo’s evaluation pipeline (you can reuse that code path).

2) Geometry-based automatic registration (when you only have PLY clouds, not known correspondences)
- Use an automatic global registration pipeline (Open3D):
  - Optionally downsample, compute FPFH features, do RANSAC global registration to get an initial alignment.
  - Refine with point-to-plane ICP.
- Advantages: fully automatic, works when there’s sufficient geometric overlap; might fail or produce wrong match if overlap is small or geometry repetitive (long corridors!).
- After registration, transform poses from the second recording into the first recording’s frame (apply the 4×4 transform to each 4×4 pose).

2) Merge (automatic geometry-based example script)
- Save the following as merge_pointclouds.py and run it. It uses Open3D to do a global registration + ICP and writes merged.ply.

```python
# merge_pointclouds.py
# Usage:
#   python merge_pointclouds.py /path/to/pointsA.ply /path/to/pointsB.ply --voxel 0.05 --out merged.ply

import argparse
import open3d as o3d
import numpy as np

def preprocess(pcd, voxel_size):
    pcd_down = pcd.voxel_down_sample(voxel_size)
    pcd_down.estimate_normals(o3d.geometry.KDTreeSearchParamHybrid(radius=voxel_size*2, max_nn=30))
    fpfh = o3d.registration.compute_fpfh_feature(
        pcd_down,
        o3d.geometry.KDTreeSearchParamHybrid(radius=voxel_size*5, max_nn=100),
    )
    return pcd_down, fpfh

def pairwise_registration(source, target, voxel_size):
    src_down, src_fpfh = preprocess(source, voxel_size)
    tgt_down, tgt_fpfh = preprocess(target, voxel_size)

    # RANSAC global registration (coarse)
    distance_threshold = voxel_size * 1.5
    result = o3d.registration.registration_ransac_based_on_feature_matching(
        src_down, tgt_down, src_fpfh, tgt_fpfh,
        mutual_filter=True,
        max_correspondence_distance=distance_threshold,
        estimation_method=o3d.registration.TransformationEstimationPointToPoint(False),
        ransac_n=4,
        checkers=[o3d.registration.CorrespondenceCheckerBasedOnEdgeLength(0.9),
                  o3d.registration.CorrespondenceCheckerBasedOnDistance(distance_threshold)],
        criteria=o3d.registration.RANSACConvergenceCriteria(4000000, 500),
    )
    print("RANSAC result:", result.fitness, result.inlier_rmse)

    # Refine with ICP (point-to-plane)
    icp_thr = voxel_size * 0.4
    result_icp = o3d.registration.registration_icp(
        source, target, icp_thr, result.transformation,
        o3d.registration.TransformationEstimationPointToPlane()
    )
    print("ICP refined:", result_icp.fitness, result_icp.inlier_rmse)
    return result_icp.transformation

def merge_clouds(a_path, b_path, out_path, voxel=0.05):
    a = o3d.io.read_point_cloud(a_path)
    b = o3d.io.read_point_cloud(b_path)
    print("Points A:", np.asarray(a.points).shape, "Points B:", np.asarray(b.points).shape)
    T = pairwise_registration(b, a, voxel_size=voxel)  # transform B -> A
    b.transform(T)
    merged = a + b
    merged_down = merged.voxel_down_sample(voxel)
    o3d.io.write_point_cloud(out_path, merged_down)
    print(f"Merged written to {out_path} (voxel={voxel})")

if __name__ == "__main__":
    p = argparse.ArgumentParser()
    p.add_argument("a")
    p.add_argument("b")
    p.add_argument("--voxel", type=float, default=0.05)
    p.add_argument("--out", default="merged.ply")
    args = p.parse_args()
    merge_clouds(args.a, args.b, args.out, voxel=args.voxel)
```

Notes for the script
- Adjust voxel (downsample) size to your scene scale (0.02–0.1 m typical).
- If RANSAC fails (fitness low), you’ll need manual correspondences or a different initial alignment.

3) Merge using the repo’s Umeyama + ICP (pose-based) — if you have matching keyframes

  - umeyama_registration(source_points, target_points) -> 4x4 Sim(3) transform
  - icp_registration(source_points, target_points, icp_threshold=0.1) -> 4x4 transform
- Workflow:
  - Identify corresponding point sets (e.g., from overlapping keyframes). The evaluation code in benchmark/datasets/* shows how they derive pixel-wise correspondences and call umeyama_registration (see benchmark/datasets/* evaluate_pointcloud).
  - Example (pseudo):

Merging poses / traj.txt
- After computing transform T (4×4) that maps cloud_B → cloud_A:
  - Load each 4×4 camera pose P_B (camera-to-world C2W) from B’s traj.txt and do P_B_in_A = T @ P_B (or depending on convention maybe apply inverse; check the repo’s apply_transform implementation).
  - Append/merge the transformed poses into the primary traj.txt for the merged scene.
- The repo’s evaluation saves traj_transform.txt (Sim(3) matrix) — you can follow that format so the viewer can auto-align.

Practical tips / pitfalls
- Overlap is essential. If two recordings don’t have good overlapping geometry, automatic alignment often fails; add some overlapping views (a few seconds of the same doorway/corridor) when re-recording.
- Scale: model outputs may be in meters but still require Sim(3) for scale; Umeyama solves scale, ICP does not.
- Repetitive geometry (long similar corridors) confuses feature matching / RANSAC; use manual correspondences or extra sensors (floor markers or AprilTags) if needed.
- After merging, voxel downsample and outlier removal (statistical filter) to keep file size manageable.
- For many recordings, consider a pose-graph / global optimization (loop closures) approach — tools like COLMAP, OpenVSLAM or custom pose-graph optimization work well to jointly optimize many sequences.

  - Index with Faiss (flat or IVFPQ) for nearest neighbor lookups. For mobile, prefer small CPU-friendly index or store descriptors and brute-force if small.
- Pose conventions: use the repo’s C2W (camera-to-world) convention and store transforms as 4×4 floats.

2) Map building and iterative merging (lab/cloud side)
- Tools: LingBot‑Map (this repo), Open3D, COLMAP (optional), Python scripts, Faiss, optionally pose-graph optimizer (g2o / Ceres / Open3D GlobalOptimization).
- Basic flow per new recording:
  1. Run LingBot‑Map on video to produce traj_B and points_B.ply.
  2. If this is the first recording, export map_A = points_B.ply, save keyframes and descriptors for B, build index.
  3. If map_A exists, register new recording:
     - Attempt pose-based alignment: find correspondences between B keyframes and A keyframes (image retrieval + local feature matching). If you have matching frames, compute Sim(3) with Umeyama (repo has umeyama_registration) on corresponding 3D points. Refine with ICP (icp_registration). This yields transform T_B->A.
     - If pose-based fails, run geometry-based global registration: convert clouds to downsampled PLYs, RANSAC global registration → ICP refinement.
  4. Apply the transform to traj_B and points_B to bring in A’s frame. Merge point clouds and keyframes, remove duplicates (voxel downsample or statistical outlier removal).
  5. Optionally run pose-graph optimization over all camera poses and loop closures (COLMAP or Open3D pose graph) to reduce global drift.
  6. Rebuild/export map.glb and nav_graph.json and re-index keyframes.
- Incremental/iterative behavior: each new uploaded recording is merged into the existing map using the same process. Keep versions and allow rollback.

Files / code already in LingBot‑Map to reuse

- The repo’s viewer/glb exporter: lingbot_map/vis/glb_export.py and point_cloud_viewer.py to generate GLB and visualize.
- demo.py/demo_render for producing per-recording outputs (traj.txt, points.ply).

3) How mobile localization works (the heart of your privacy-friendly UX)
Goal: user opens app, takes 1 or 2 photos (broad area from standing position); app localizes user into the offline map and shows an avatar; afterwards the user may move, but camera can be off most of the time.

High-level components on device:
- Map loader: loads map.glb, nav_graph.json, and the keyframe DB (descriptors & 2D→3D).
- Photo matcher (single-shot localization):
  - Step A (retrieval): compute a global descriptor from the user photo (NetVLAD or lightweight DINO / MobileNet embedding) and query the Faiss index to get top K candidate keyframes.
  - Step B (local matching): for each candidate keyframe, run a local feature matcher (SuperPoint or ORB if speed/size matters) between the user photo and keyframe image to produce 2D–2D matches.
  - Step C (2D→3D correspondences): for matched keypoints, the keyframe DB stores associated 3D points (from LingBot predicted depth projected into world). Use these to form 2D (user photo) ↔ 3D (map) correspondences.
  - Step D (solve PnP + RANSAC): compute camera pose in world coordinates using PnP + RANSAC (OpenCV's solvePnPRansac). If enough inliers and low reprojection error → success.
  - Output: initial C2W pose of the mobile device; set avatar position & orientation.
- Tracking after localization:
  - Option 1: ARKit / ARCore tracking (best): if the user allows brief camera usage, start AR session, get high-accuracy VIO pose, then map AR pose into map coordinates using the previously computed transform. AR runs with camera on and is accurate—useful when the user accepts.
  - Option 2: IMU-based dead-reckoning (privacy/no camera): after initial pose, use IMU sensors to track motion — fusion of accelerometer + gyroscope + magnetometer using a Kalman or complementary filter and a step detection algorithm:
    - Use step detection + stride length estimation to update position along heading (Pedestrian Dead Reckoning). Heading from gyroscope + magnetometer; step distance either fixed or adaptive (calibrated).
    - Use fused sensor filter (AHRS) for orientation and drift correction.
    - Periodically ask the user for a re-localization photo to correct drift, or silently accept a small drift over time.
  - Option 3: Hybrid: run IMU tracking continuously, but allow optional very brief AR sessions (camera on for 2–3 s) to correct drift when user taps “recenter” or walking through known landmark triggers automatic re-localize.
- Floor / 3D location: include barometer data (if available) to disambiguate floors, or let the system match photo to a keyframe that includes known floor id. The map package should store floor partitioning (height ranges).

Privacy UX: user only needs to take 1–2 photos at start (or tap a “relocalize” button later). No continuous camera streaming is required. Photos and descriptors can be processed fully on-device if desired (no server call).

4) Navigation graph & routing
- From the merged map, extract a 2D navigation layer per floor:
  1. Detect floor planes (RANSAC plane fitting on point cloud) and compute planar projection for points in each floor slab.
  2. Generate occupancy grid (voxel grid projected to 2D), remove small obstacles.
  3. Skeletonize free space to get a topological graph or build a grid-graph and then simplify to a graph of nodes (intersections, doorways).
  4. Build nav_graph.json: nodes {id, x,y,z, floor}, edges {to_id, weight(distance), meta (stairs/elevator)}.
- On device, run Dijkstra/A* on that graph; return waypoints to display as 2D top-down route and 3D overlay (map.glb).
- For turn-by-turn: transform waypoints into relative directions and show arrows on the map overlay.
